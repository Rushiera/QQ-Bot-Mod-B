### 2.2 三处实现变更（都写在脚本头部注释里，防下一个人改坏）

1. **根可以是文件**——`walk()` → `collect()`：目录递归、单文件直收（`app/src` 同层还有 `.css` / `fonts/`，按目录登记会把非 js 卷进来）。`fs.statSync` 不存在即跳过，不抛。
2. **根缺失要点名**——`present` / `absent` 分流；缺根不静默缩面，由输出字段 `missingRoots` 列出（`L1/Wisdom.md` §1.16-⑤ 集合缩水的对口治理）。
3. **报错面按根相对**——`relOf()` 把 `problems[].file` 写成 `business/routes.js` / `web/server.js` 形态；不写的话多根混在一起时读者分不清这个 `routes.js` 是哪个面的。

### 2.3 扩围的实际收益（不是凑数）

`web/` 三件（`business-proxy.js` / `groups-api.js` / `server.js`）当前内部**零相对导入**（`text-grep from './` 命中 0，只有 `node:` 内置导入），所以本轮它贡献的符号数是 0。扩围的价值在于：L9 新增的 `business-proxy.js` 与改过的 `app.js` 下一次加相对导入时，这一面已经在守——`app.js` 装配层新增一次 `import { x } from './navigator/y.js'` 即可让启动闪退，而旧的单根扫描看不到它（正是 `R5-L16.md:165` 登记的盲区）。

## 三、`verify-qqagent-boot` 环境面出口

### 3.1 判据（不是「遇错就跳过」）

- SKIP **只在两条件同时成立**时给出：① 锁文件解析出 PID ② `process.kill(pid, 0)` 探活成功。锁残留（进程已死）→ 照常真跑，不打折。
- SKIP 回执是结构化 JSON，含 `reason`（带 PID）/ `stage` / `lockFile` / `howToReallyRun` / `note`——`grep SKIP` 能定位到「被谁占着、怎么解」。
- 双检测点：`pre-start`（启动前读锁）+ `start-throw`（预检与 `start()` 之间锁被抢走的竞态，从异常文本里取 PID 同口径处置）。
- **强制真验**：`--require-live`（或 `QB_VERIFY_REQUIRE_LIVE=1`）——此时锁被占按 FAIL 计，退出 1。防「SKIP 变成永久遮羞布」。
- **换数据根真跑**：`--data-dir <dir>`（或 `QQ_AGENT_DATA_DIR`）——起一个自有 `config.json`、独立端口的临时数据根即可完成真验，**不必停业务面**。此前脚本无条件把生产根写进 `env`，覆盖入口不存在，这是「只能等主干停业务面」的真正原因。

### 3.2 三种情形回执（全部实跑）

**情形 A · 生产数据根 + 业务面在跑（PID 19152 持锁）→ SKIP，退出 0**

```

{
  "ok": true,
  "skipped": true,
  "reason": "SKIP: 单实例锁被占用（PID 19152）",
  "stage": "pre-start",
  "lockFile": "D:\\Mau\\WorkSpace\\QQBotB\\_unpack\\data\\qq-agent.lock",
  "howToReallyRun": "换数据根真跑：node tools/verify-qqagent-boot.mjs --data-dir <dir>；或停掉 PID 19152 后重跑；或加 --require-live 让锁被占按 FAIL 计",
  "note": "环境占用非代码回归——锁解析出的 PID 已探活确认；本档不计红"
}
```

**情形 B · 同上加 `--require-live` → FAIL，退出 1**

```

**情形 C · 独立数据根（无锁）→ 真跑，退出 0（真验未被 SKIP 替代）**

{
  "ok": true, "port": 3410,
  "api": { "baseUrl": "", "model": "", "hasKey": false },
  "snowluma": { "wsUrl": "ws://127.0.0.1:3001", "hasToken": false },
  "persona": { "botName": "小鲸鱼", "roleTextChars": 6148 },
  "allow": { "groups": 0, "private": 0 },
  "contextTier": 4, "systemPromptChars": 5140, "sessions": []
}
[onebot] 获取登录信息失败: OneBot get_login_info HTTP 403
（退出码 0）
```

> 末行 `OneBot get_login_info HTTP 403` 来自临时数据根没配 SnowLuma 令牌——属该根配置面事实，不是本脚本判据（脚本判据是 `/api/sessions` 与 `/api/prompt-preview` 可达 + 启动会话可见，两者均过）。
> 另测：把临时根里塞入活锁 PID（19152）后跑同一命令 → 走情形 A 的 SKIP 出口——证明 `--data-dir` 路径下的锁检测同样生效，不是只在生产根上闭眼跳过。
> 临时数据根 `WorkSpace:tools/CatTemp/qqbotb-l5-data`（含 `config.json` / `sessions/` / 锁）跑完已 `file-delete` 入回收站，不留在工作区。

### 3.3 一处实测缺陷（首版即踩，记下来）

首版 `skipLocked()` 用 `console.log(...)` + `process.exit(0)`，跑出来 **退出码 0 但零输出**——Windows 下 stdout 是管道时 `process.exit` 会截断未刷出的缓冲。改为 `fs.writeSync(1, text)` 同步写 fd 后再 `exit`。这条与 `L1/Wisdom.md` §1.16-⑥「成功伪装成已验」同族：一个「SKIP 但什么都不打印」的守门脚本，比红的脚本更难察觉。

## 五、遗留与登记（都不在本轮写面内）

### 5.1 `verify-qqagent-cwd` 3/21 红（退役脚本，既有口径不一致）

三条红全指向启动器脚本的**旧形态**：

```
FAIL 启动QQAgent.bat：cd /d 钉到 _unpack
FAIL 启动QQAgent.bat：start 行仍在
FAIL 启动QQAgent.vbs：CurrentDirectory 钉到 _unpack
```

断言行位置：`tools/verify-qqagent-cwd.mjs:102`（找 `cd /d "%~dp0_unpack"` + `[qqagent-cwd-patch:launcher-bat]`）· `:103`（找 `start "" "%~dp0_unpack\QQ Agent.exe"`）· `:105-106`（找 `sh.CurrentDirectory = "D:\Mau\WorkSpace\QQBotB\_unpack"`）。

实况：`启动QQAgent.bat` 现为 legacy 入口 **别名**，正文只有一行 `call "%~dp0tools\entry.cmd"`（该文件 `:15`，头注 `Generated by tools\apply-entry.mjs`），本身既无 `cd /d` 也无 `start`；`启动QQAgent.vbs` 同理是别名（`:12` `sh.Run "cmd /c " & q & root & "\tools\entry.cmd" & q, 0, True`，无 `CurrentDirectory` 赋值）——钉 cwd 的职责已下沉到 `tools/entry.cmd`（`:40` `cd /d "%APPDIR%" || exit /b 1`，其中 `APPDIR=%ROOT%\app`，即钉到 `app\` 而非 `_unpack`）。而三条断言仍按旧形态找 `_unpack`。
**这是断言陈旧，不是代码回归**：第 8 条「`启动QQ机器人.bat`：cd /d 钉到应用目录」实测 PASS（目标文件是 `_unpack/resources/app/启动QQ机器人.bat`，`:18` `cd /d "%~dp0" || exit /b 1` + `:17` 标记 `[qqagent-cwd-patch:app-bat]`，未改形态），说明脚本的检测逻辑本身工作正常，只是根目录那两个入口文件换了形态。
该脚本在 `tools/verify-suite.mjs:50` 的 `SKIP` 集合里（同行注释「已判退役（D1：cwd 2 点失效）」），故不进守门档、不构成回归。
**处置建议**：要么把三条断言改成检查 `tools/entry.cmd` 的 `cd /d "%APPDIR%"`（与 2026-10-12 入口统一后的形态对齐），要么按退役清出目录——需主干定，本轮不动（写面外，且属「退役脚本的断言是否重写」这一判断）。

### 5.2 守门档 28/28 的 1 条 SKIP 要如实读

`verify-qqagent-boot` 在守门档里**退出 0 走的是 SKIP 出口**（业务面 PID 19152 持锁）。所以 `28/28` 的正确读法是「28 条不红」，不是「28 条都真验过」。真验由 §三-情形 C 独立数据根补齐。若要把「真验」变成守门档的硬要求，主干可在合龙环节（停业务面后）跑一次 `--require-live`。

### 5.3 扩围的负向自测（已做，附实跑）

`problems: 0` 只证明「现有代码面没有缺失符号」，不证明「脚本仍能检出缺失」——守门脚本恒绿是最难察觉的失败形态。故本轮补了负向自测，做法**不碰 `app/**`**：脚本加 `--src <dir>` 覆盖入口（等价 `VERIFY_IMPORT_SRC`），指向一个刻意坏掉的夹具目录。

夹具（`WorkSpace:tools/CatTemp/negtest`，`a.js` 只导出 `foo` / `baz`，`b.js` 却 `import { foo, missingSym }`），实跑：

```
node tools/verify-import-integrity.mjs --src D:/Mau/WorkSpace/tools/CatTemp/negtest
{
  "ok": false,
  "filesScanned": 2,
  "symbolsChecked": 2,
  "roots": ["."],
  "missingRoots": [],
  "problems": [ { "file": "negtest\\b.js", "from": "./a.js", "missing": ["missingSym"] } ],
  "verdict": "FAIL —— 1 处符号缺失（应用会启动即崩）"
}
（退出码 1）
```

撤掉 `--src` 后同命令回到 `filesScanned 98 / problems [] / 退出 0`——覆盖入口不影响默认守门面。夹具目录已 `file-delete` 入回收站。

### 5.4 `--src` 覆盖入口的边界（为什么它不削弱守门）

- 默认面固定 `app/src` + 11 项根清单；`--src` / `VERIFY_IMPORT_SRC` 只让**整根递归**一种形态生效（夹具不按生产根的模块名摆放）。
- `verify-suite` 调本脚本时不传参、不设该 env，故守门档扫的永远是生产源。
- 保留它的代价：多一个入口参数；收益：这类「恒绿检测器」任何时候可在 10 秒内自证还能红。
