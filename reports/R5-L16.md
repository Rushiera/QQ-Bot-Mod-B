node tools/verify-ui-contract.mjs          # 人读：逐条 FAIL + 每组小计 + PASS n/n

**三处口径设计（写进脚本头部注释，防下一个人改坏）**

1. **登记形态按「生效」判，不按字面判**——契约 §三-2 只要求「每块暴露 `window.__views.<name>`」；
   `registerView(name, view)` 是 `_shell.js` 提供的等价写法（内部即 `views[name] = view`）。
   故断言 `views.<name>=` 或 `registerView('<name>', …)` 二者任一成立即过。
   形态矩阵由 `--json` 的 `forms` 输出，实测：

   | 块 | 形态 |
   |:--|:--|
   | `sessions.js` · `chats.js` · `settings.js` | `registerView(...)` |
   | `memory.js` · `usage.js` · `skills.js` · `plugins.js` | `views.<name> =` |

2. **`_shell.js` 从「零裸 fetch」组豁免**——`api()` 的实现本体就在该文件（`_shell.js:162` 的 `await fetch(path, init)`），
   把实现者算成违规会让这条断言永远红；契约 §三-4 约束的是**消费方**（视图块），不是提供方。

3. **详情只在失败时保留**——首版把 detail 无条件存进结果，`--json` 里 57 条 PASS 全带「文件缺失 / 未找到」的失败文案，
   人读会以为红过。已改为 `ok ? '' : detail`（同轮实测踩到，即修）。

## 六、契约与卡的差异（一处，已按契约实现并报主干）

`tasks/R5.md` §四 L16 判据 ① 写的是「每块是否调 `registerView`」；
`app/ui/views/_index.md` §三-2 写的是「每块只暴露一个全局挂载对象：`window.__views.<name> = { mount(el), refresh() }`」。

**实况**：七个块里 3 块走 `registerView(...)`、4 块直接写 `views.<name> =`（`--json` 的 `forms` 可核）。
按卡的字面判会误判 4 块为失败，而它们完全合规。**本线按契约（生效面）判**，并把形态矩阵输出供主干核对——
若主干要求统一形态，那是 L2–L8 的活，不是 L16 的判据问题。
