## 三、实现要点（为什么这么写）

### 3.1 为什么必须改 `server.js`（卡面前提缺陷的实况复验）

`server.js:111` 是 `const handler = api[key];`——`key = '<METHOD> <pathname>'`，**精确匹配，无通配**。所以「api 表加一项覆盖 `/api/biz/*`」不成立；卡面两条路（枚举 73 条 / 前缀兜底）中选 ②，理由：枚举必漏，且业务面路由表会随轮次增长。

兜底位置的三条纪律：
- **在 `if (!handler)` 之内**——`api[key]` 命中就先走命中，前缀兜底在语义上永远排在精确匹配之后（判据 ⑥ 的行为依据）。
- **在 `serveStatic` 之前**——否则 `/api/biz/sessions` 会被静态托管接走回 404（实测基线：改前 `GET /api/biz/sessions` → `404 {"ok":false,"error":"not found"}`）。
- **异常不静默**——`bizProxy` 抛错回 500 并 `log.error('web', ...)`，不回落静态、不吞。

### 3.2 地址解析为什么委托 `business`

`business.js:109-146` 的 `resolveBase()` 已经做了三件本线不应重复的事：配置地址优先 → 端口段 3210..3219 探测 → **响应必须含 `allow.groups` 才算业务面**（`:98-102`）。再写一套 = 两个真相源，业务面换端口时必有一处漂移。

代价与处置：每次 `resolveBase` 会多一次 `/api/config` 请求——用 `base` 缓存 + `resolving` 单飞消掉（`business-proxy.js:39-42` `:82-100`），转发失败时清缓存由 `business` 重解（`:183`）。

### 3.3 三类失败的判定树

```
__bizProxy 入口
 ├─ 方法不在 {GET,POST,DELETE}  → 405  warn 出声（不静默丢弃请求）
 ├─ send() 抛 AbortError        → 504（不分首轮/重试轮）
 └─ 其它异常
      ├─ 清 base 缓存 → 重试一次（业务面重启换端口的最常见形态）
      └─ 仍失败 → 502，正文 = `业务面不可达（127.0.0.1:3210）：<detail>`
                  detail 剥掉客户端同义前缀防重复（:194）
```

**注**：业务面**自己**回的 4xx/5xx **不走异常路径**——`send()` 返回 `{status: response.status, body: 解析结果}`（`:143-151`），由 `server.js:120` `sendJson` 原样出帧。这条区分是判据「透传」与「不可达」不互相污染的关键：业务面回 404 不该被翻成 502。

## 五、与卡面的一处收窄（报备）

兜底判据由卡面字面 `pathname.startsWith('/api/biz/')` 放宽为：

```js
if (bizProxy && (url.pathname === '/api/biz' || url.pathname.startsWith('/api/biz/')))
```

**理由**：前端若误写不带尾路径的 `/api/biz`（L2–L8 的 `api()` 调用可能拼出这个形态），改前落到静态 404（`{"ok":false,"error":"not found"}`，与「业务面 404」形态不同），改后统一走代理回业务面 404，失败形态收敛到一处——与本线「把失败形态收敛到一处」的目标同向。

**回退**：一行改回 `startsWith` 即可，无副作用。判为越界则回退。
