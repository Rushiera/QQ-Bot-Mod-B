## 一、面（做了什么）

左栏群选择器 + 右栏历史存档，按天分组、新在上；右栏头三个控制：「加载更早」往旧翻一批、「回到最新」重置、「刷新」（左栏工具条，同时刷群列表与当前群首批）。

| 区 | 内容 | 取数 |
|:--|:--|:--|
| 左栏 | 全量群列表（键 / 群名 / 条数 / 未读数 / 最近时间）+ 过滤框（群号或群名）+ 计数 `可见 / 全量` | `/api/biz/chats` |
| 右栏头 | 群名 / 群键 / 存档总数 / 已载入数 / 第几批 / 是否到最早 / 更新时间 | 群 meta + 本地累加 |
| 右栏体 | 消息流（发送者 / 时间 / 媒体数 / 未读徽标 / 自身徽标），按 `YYYY-MM-DD` 分节 | `/api/biz/chats/<group_xxx>/messages?limit=` |

空态用 `empty()`（「还没有消息存档（等白名单里的群 / 好友来消息）」/「这个群还没有存档消息」），失败态用 `fail()` 且文案带 `3210`，「外壳未就绪」单独区分（`window.__ui.api` 缺失时提示等 L1 落地，不混成业务面不可达）。

## 二、🔴 翻页口径与卡的差异（主线决策点，报主干知悉）

**卡的判据**（`tasks/R5.md` §四 L3 验收 ③）：两批（`?limit=` 不同）消息 id 集合无交集。

**实况**：消息路由 `^/api/chats/(group|private)_(\d+)/messages$`（`app/src/business/routes.js:1463-1472`）只读 `limit`，**不吃 `offset`**；`limit` 语义 = `store.recent(chatKey,{limit})`（`app/src/business/store.js:273-279`）取**最近 N 条**。`store.recent` 本身支持 `offset`（`:273`），但路由没透出。

**处置**（`chats.js:10-16` 文件头已写明）：不自造端点（§0-6 契约不可自扩）——

- 第 k 批 = 请求 `?limit=k*PAGE`（`PAGE=100`），再切掉窗口里前 k-1 批已覆盖（更新的）那一段，只留更早的 `PAGE` 条；
- 后一批恒为前一批之前 → 两批 id 天然无交集；连翻时整段追加到**尾部**（列表「新在上」，第二段必须排在下面）；
- 代价：`?limit=` 随翻页单调增长（第 3 批请求 300 只落 100）。上限 `MAX_BATCH=30`（3000 条，与原版单次 `limit=3000` 同量级）。
- `offset` 一旦在路由透出，`loadBatch` 改两行即可变真分页。
